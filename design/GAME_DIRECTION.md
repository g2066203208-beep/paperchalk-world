# 未命名游戏 · 核心玩法方向（草案）

> 核心不是“审核谁能入境”，而是“几位值夜班的人在同一间杂货铺中，通过做生意、观察陌生人及对照彼此看到的细节，判断谁正在冒充人”。

## 游戏场景和基调
一间临街的二十四小时小店。夜里只有一盏大灯持续亮着。怪事不是从假证件开始：零钱找错、刚卖出的面包再次出现在货架上、某位熟客的影子先于本人到店、十年前注销的会员卡忽然出现。有些异常是店铺故障，有些是普通人尴尬的秘密，只有少数是“借脸者”。错误地驱逐真人会损失人情和生意；放进借脸者可能使真实顾客失踪。

## 现有原型的关键缺陷
当前游戏主要依赖文字观察与投票，缺少场景里的可操作物件、顾客连续动作和可见状态变化，不能视为完成的游戏。开发优先实现三分钟可操作营业流程，并按 [真实交互验收](PLAYABLE_GATE.md) 验证。

## 原创多人设计
不是四个头像和四张投票按钮：**共同的一间店、四个可自由切换的实际工作位**，每个工作位能对同一事件做不同操作，而且操作直接改变其他人的情况。

1. **柜台**：与顾客交谈、询问商品、找零、让对方稍等。
2. **货架**：补货、检查商品编码与现存数量、找曾卖出的物品。
3. **旧账**：查看收据、电话留话、邻里熟客的连续来访记录。
4. **窗边**：调外灯、拉帘、观察雨伞、脚印与倒影。

1 人可以轮流切换所有工作位；2 人已经能一人应对顾客、一人调查；3–4 人同时分工。后续开放“玩家扮路过者”对抗模式时会再设计，不和第一版的合作机制混成一团。

多人局里所有人都能做出“放行／留店观察／婉拒交易”提议，最后需要超过半数确认；2 人意见冲突无法推进，需要进一步调查。玩家共享“线索板”，但每位玩家可以独立查看证据，自己的浏览状态不会强制覆盖队友。客户端不能自己决定正确答案；判定在房主端统一计算。

## 每晚 8–12 个可辨识事件
**不是依靠绝对规则抓瑕疵。** 人也会记错名字、证件也会过期，伪人也会刻意模仿得完美。关键在于证据链：对话 ↔ 物品 ↔ 店铺记忆 ↔ 街道事件。每张卡至少有两种合理解释，只有交叉验证才稳定。熟客会再次来访且记得玩家的态度。

示例：顾客买一把伞，收据说上周已经买过一次；窗边监控见到一把一模一样的伞卡在门外；货架显示同批次只进了两把。必须推断究竟是库存错误、失物找回还是谁在复制物品。做出行动决定会改变后续来访和店里库存。

## 当前主美原则（以用户提供的冬夜小店参考为目标）
采用统一像素密度、冬季冷蓝街景与室内暖橙光、狭窄真实售货窗口的空间纵深。全部正式角色、商品、家具、窗景及动作使用 GPTIMG 生产原创可拆分资产，保持相同镜头高度、轮廓与色彩规则。每张资产需经过透明边缘清理、裁切、分层和浏览器实机验收；禁止把整张效果图伪装成可玩游戏，也不能将参考游戏素材直接复制进仓库。

美术结构不能是“一张游戏截图”：店内远景／柜台／店门与窗户／货架／灯光／人物前后层／表情／手部道具／纸张／按钮图标全部独立文件或程序化元素。最终文字用真实字体渲染；生成图上的汉字不进入正式 UI。所有资产要检查比例、叠放层级、透明边缘和移动端 1x/2x 显示。

## 手机体验与发布
- 以 360×800 CSS px 为基础设计，支持 20:9、19.5:9、平板；利用 safe-area 适配异形屏和系统手势条。
- 单列竖屏，上半区域聚焦顾客和窗景，中间工作位切换，下半是大字证据抽屉，底部固定三个明确动作；界面 44–48dp 触控目标，不将桌面游戏强行缩小。
- 安卓壳以 GitHub Pages 提供最新网页内容，启动取最新版本；本地保存可放 WebView 应用私有存储。**APK 壳自身无法无提示静默替换**：系统安装更新仍需用户同意，持续保持签名一致才能保留本地存档。正式 release 需配置专用的持久化签名密钥，不应把私钥提交到公开仓库。
- GitHub Actions：游戏逻辑回归、双浏览器联机测试、Android APK 构建、版本记录与截图。
