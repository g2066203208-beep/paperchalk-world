# 冬季路边小店｜完整游戏制作总提示词 v2.0
> 适用项目：`g2066203208-beep/paperchalk-world`（游戏正式名称未定）
> 本文为**未来开发执行规范**，并不表示以下剧情、系统或素材已经实现。
> **最新用户确认的具体要求优先**。本文件在故事、美术和交互方向上覆盖旧文件中的冲突内容；原仓库存在的旧电池回收、开柜门、点击放大、无意义业务堆砌、伪人判断等设计，不可因为已有代码就强制保留。

## 0. 角色、工作方式与不可推卸的责任
你同时担任游戏总监、主笔、叙事设计师、系统策划、主美、动画总监、关卡与地图设计师、交互设计师、前端/网络工程师、测试负责人和发行制作人。你的职责不是向用户展示草率概念、罗列功能或不断询问基础问题，而是主动研究成熟作品的**艺术表达方法**，做出连贯设计、真正接入现有游戏、亲自测试、发现缺陷并修好。

每次开发先读取仓库、当前 main 提交 SHA、最近一次 CI/部署状态、实际页面、入口、核心状态与存档结构。逐项标记 Existing / Rework / Missing / Tested；不要误把历史实验、PNG 裁片或文字计划视为完成品。技术路线需要成本/兼容性证明；优先在现有 ES modules + Canvas + WebRTC + GitHub Pages + Android WebView 测试壳上增量改造，未经证明不得为了“专业”擅自换引擎。旧存档和联机能力不能被静默破坏。

**独立决策原则**：对细节先自行调研、绘制或编程、预览和测试；只有真正改变游戏身份或用户已经否决的核心美术方向，才需要征求用户判断。一次只向用户展示经检查的最佳结果，不提交未经审视的多张拼盘图。不能使用“已经完美”之类不能核实的描述。

## 1. 唯一艺术与情感目标
这是一款以**俄罗斯式冬季灰色气质、文学性的日常悲伤、人与人的有限温柔**为核心的小店叙事游戏。玩家被繁忙与逼仄的生活压得透不过气，走进临街小卖部，却在风雪、缓慢交谈、沉默、热茶和被人记得的细节中，找到一点“终于能长舒一口气”的安宁。

绝不做：童话式甜腻治愈、霓虹赛博朋克酒保店、恐怖标签商店、无意义工作模拟器、夸张连环反转、为了扩大内容而增加的回收电池业务、统一好感度刷分、强迫玩家达成每日 KPI。**安静、拒绝交谈、提前打烊、凝望窗外也必须是被尊重的玩法选择。**

艺术方法参考（只能研究镜头/留白/色彩/静止节奏，不得临摹受保护的具体造型）：列维坦与瓦西里耶夫的俄国景观空间重量、塔可夫斯基电影的时间感、哈默修伊的室内灰阶、考里斯马基电影里的日常克制、《完美的日子》的细微感官观察。悲伤必须从人物困境和环境细节自然出现；禁止旁白说教“你感到孤独”“这是治愈的地方”。

## 2. 核心游戏循环：简化动作，深化意义
**玩家看见顾客 → 选择接待/沉默 → 倾听一句话或观察动作 → 直接点击所需商品 → 点击台面完成交接/付款 → 人物留下话语、关系或变化 → 继续营业、看看窗外或打烊。**

店内永远是一屏可全面观察的工作台：窗口、人物、货位、交接区和必要的订单信息同时可见；绝不点击后强行放大/切相机/被迫拖动寻找角落。普通交易不需要开柜门、开抽屉、长按或多层菜单；可见即可点，适当合并不增加戏剧意义的重复步骤。点击目标至少 44 CSS px；操作要有明确悬停/按下/成功/失败反馈，可鼠标、触屏和键盘完成。

经营只保留对故事有意义的轻量资源：时间、微薄收入、补货、灯光/取暖、顾客需求和店铺状态；除非证明增强叙事，禁止发明新的“收集—包装—交运”任务链。可设置**无惩罚慢节奏模式**，玩家选择读完整对白、看雪或暂停不被倒计时处罚。主题首先是人的生活，而不是做大做强。

## 3. 原创完整故事圣经：先写故事，后扩地图
先写一份可玩的 `STORY_BIBLE.md`，必须包含：一句话梗概、中心矛盾、三幕因果链、主题/反主题、时间与地点、主角动机、至少 8 位有自我生活的常驻人物、人物关系网、逐日/逐场景事件表、每个人不由主角支配的目标、可见伏笔与回收表、所有结局的前置条件与后果。

**建议的原创故事骨架（须经过剧作论证再定稿）**：冬季一座未命名小城，店在即将调整线路的末班公交站附近。大家都说车要停了，却没有人真正准备好告别那个夜晚仍亮着的窗口。城市不会因为主角选择就奇迹般获救；主角在如何守着、交出、移动或结束这个小小的庇护所上产生抉择。

三幕结构：
- **第一幕｜习惯**：熟人、交易与细小失约；认识城市的生活节奏，建立常客的重复动作及各自隐秘疲惫。结尾发生第一处可验证的关系变化。
- **第二幕｜缝隙**：冬雪更深、线路或建筑变迁逼近；不同人物的需求互相冲突。前期小选择改变谁来求助、谁保持沉默、哪些信息被错过；不要插入外来离奇阴谋。
- **第三幕｜留灯或熄灯**：玩家不能解决所有人的困境，但可以决定如何对待他们和自己；多种结局均具有文学尊严，不设“正确善良通关”。

故事目标可分阶段扩展到约 4–6 小时高质量内容、15–21 个关键营业日、8–12 名有持续变化的熟人、4 种有因果支撑的结局。**以上是规划目标，绝非已完成数量；不能用随机重复对白填充时长。** 小规模、独特、完成的内容胜过长而空的量产文本。

## 4. 人物系统：他们不是排队头像
人物实体包含：稳定 ID、身份/工作/日程/居住区域、可观察习惯、生活目标、人物关系、私人困难、视角局限、逐幕发展、最近互动记忆、已知事实、可触发事件、外貌母版和动作状态。角色不是永远站在便利店前等待玩家触发；在地图上有合理的日常出没，天气与时间影响来访。

关系系统不使用廉价可刷的红心。保留关系标签（陌生/见过/熟识/信任/疏远/失联等）及离散记忆事件，选择可以提高一项信任但降低另一项边界感。**NPC 彼此也有关系**，玩家不知道的一些事会在他们离开窗口后发生，通过后来一句话、信件或场景变化间接获知。

男女主角为**同等完整可选择的玩家主角**：共享故事权重、职业能力与镜头语言，只有服装体态、称呼等合适差异，绝不“男主角负责经营、女主角负责情感”。主角也是叙事主体，有疲惫、有犹豫、有自我边界，而不是沉默工具人。

## 5. 对话与选择系统：真正的文学与可测试的分支
实施独立的**数据驱动剧情图**：`DialogueRunner`、`StoryScheduler`、`ChoiceResolver`、`NarrativeState`、`DialogueView`、`LocalizationTable`。可以先评估 Ink + inkjs（适合现有 JS/Web 项目）或 Yarn Spinner 的节点/变量模型，经过小规模集成验证再决定；不可把对白写死在 Canvas render 或随机数组里。

每个对白节点至少包括：
- `id`, `speakerId`, `textKey`, `sceneId`, `conditions`, `priority`, `once/repeat/cooldown`, `choices`, `onEnter`, `onExit`, `next`, `animationCue`, `soundCue`, `cameraCue`；
- 每个选项包含 `optionId`, `labelKey`, `enabledWhen`, `effects`, `next`；
- `effects` 必须使用受校验的结构化白名单命令（设置 flag、记录人物记忆、物品交接、推进时段、触发演出、安排后续事件），**绝不以对话内容执行任意 JS**；
- 进入对白冻结或协调相关操作，选择提交只生效一次，异步动画结束后才推进；载入存档必须回到可解释的节点和确定状态；
- 无条件节点、分支合流、互斥分支、选择可见条件、默认出路、超时失败恢复都有形式化检查。每条结局路径可遍历、可进入、可结束，没有悬空指向、无限循环、人物重复领同一报酬。

选项不局限“好人/坏人”：**关心、敷衍、坦白、回避、静静听着、拒绝、换个话题**都可能合理。至少一部分选择延迟一个营业日或一章才显现后果；部分微小选择当场通过停顿、手势和对白节奏体现。允许玩家不选，文学性沉默也是选择，且不得陷入 UI 死锁。重要抉择既改变关系，也反映到地图、商品、来访顺序、环境物件或结局台词。

**对白质量标准**：每位熟人有可辨的语气、用词、话题回避和说话节奏；多用观察、潜台词、留白、物件和行为，少用直白设定解说、烂梗、泛滥“温暖治愈”台词。对白不超过需要表达的长度；文字可完整回看、可跳过已读演出、允许关闭打字机效果。逐句审查是否符合人设、关系与当地生活。

示范情境（只作节奏示例，非可重复模板）：临关门，公交司机在窗外站了许久，说：“末班车今天没晚点。” 玩家可回答“你看着不像高兴”、只把热杯推过去，或先不说话。真正的差别发生在后来他是否愿意告诉别人车站要停用，而不是立即弹出“好感度 +5”。

## 6. 地图与时空系统：小而完整，有生活
建立 `WorldMap`、`SceneGraph`、`LocationState`、`ClockWeather` 和可回访节点。核心围绕店面、雪中街道、公交站、居民楼入口、便宜食堂、桥边/河堤等**约 5–7 个有独特叙事功能的区域**，地理关系、视线、到达方式、营业时间和人物日程必须一致。地图不是清单图标墙；每区至少有可观察环境变化、人物事件和因故事改变的细节。

场景渲染用可编辑**独立图层**：天空 / 远处住宅 / 树木电线 / 中景建筑 / 地面雪 / 马路 / 店屋 / 前景遮挡 / 雪粒 / 灯光 / 可互动对象 / 角色 / UI。保留世界坐标与统一素材母版，手机横竖屏仅变视口/响应式排版，不另画一套世界。室内仍固定全景，不因地图存在恢复点击缩放。

地图和事件的关联需声明 `locationId`, `exits`, `conditions`, `spawn`, `occlusion`, `interactionBounds`, `timeWindows`, `weatherOverrides`。优先评估 Tiled 的分层 JSON 与 object/custom properties，或自有轻量 JSON schema，实际验证导入/导出和碰撞/热点精准一致再选。地图镜头没有必要漫游，就采用清晰的场景切换，不为了假“开放世界”牺牲完成度。

## 7. 美术总监规范：一套语言，不是素材大杂烩
**背景世界**：低饱和铅灰、雾蓝、暖灰白、旧建筑褪色色块；俄罗斯冬季不是全黑，也不是奢侈咖啡馆式通体金黄。远景和负空间远比繁琐摆件重要。程序绘制天空、雪、几何、简洁建筑、柜台与 UI；保留像素/扁平图形的节奏，禁止廉价缩图马赛克、油画滤镜和虚假粒子辉光。

**角色必须由 GPT 生图设计、按单个角色高分辨率独立生产**，并保留原创主素材。已确认的角色风格优先级：
1. 所有角色脸/露出的皮肤是**完全纯黑的无五官人体剪影**，不能画皮肤高光、眼鼻嘴、表情；
2. 头发允许着色，但**整块只有一个固有色**，无高光、渐变、发丝阴影色块；
3. 衣服、帽子、围巾、外套、鞋包用**协调的正常低饱和彩色**，每种材质以固有色 + **少量有造型逻辑的硬边暗面色块**表现体积；不是服装也全黑白；
4. 强调**“简约不简单”**：从帽顶、肩宽、衣摆、腿、靴的整体轮廓出发，配饰极少且每一件都改变人物识别性；拒绝大量带子、口袋、假功能绑带、花哨编织、无意义丝带；
5. 一次只生成**一张完整单人全身母版**，透明背景、头脚不切、四周留安全边距，不生成多角色拼盘或设定页；先对照原参考人物的轮廓、衣服结构、光暗组织审查，再制作另一性别或动作；
6. 动作变体以相同角色母版为约束，身体比例、服装结构、颜色和锚点不变；不得每张变体都换脸换人；
7. 资产源文件按人物/背景/物件/动作分层保存，manifest 定义原尺寸、alpha、pivot、frame bounds、版本、来源、许可。运行时可由**已批准单件源素材**编译图集优化，图集绝不能替代可编辑单件原稿。

角色不能直接把 1500px 光滑立绘无处理地塞入 180px 像素街景；要实机比对轮廓密度、色板、像素缩放与遮挡，选择统一的混合美术管线，确保视觉协调。

## 8. 动画与电影化演出系统
将动画分为 `SceneAmbience`（低速雪、光线、远树）、`CharacterState`（enter/idle/listen/speak/hesitate/receive/leave）、`InteractionSequence`（拿货/放下/递出/接过/付款）、`CinematicCue`（留白、短暂静止、过场）。所有动画由显式状态机驱动，状态有进入/退出条件、事件触发点、超时兜底、可中断/可跳过、主客机同步的权威事件 ID。

因为人物无五官，**情感依靠姿势**：头部角度、肩线、手部停留、脚步迟疑、物体接触时机；避免夸张夸张弹跳和“呼吸缩放”替代真实动作。动画必须体现在每一次交接的真实轨迹、锚点和遮挡，不允许商品穿越衣袖、窗口或凭空消失。下雪应有层次但不抢焦点；允许“静态模式”关闭不必要动态。

列出每个角色的必备动作，先实现同一角色的 `idle → enter → talk → receive → leave` 完整闭环，再扩展角色。录制至少一段完整顾客从街道到窗前、交谈、交易、离开的连续实机演示；不能拿动画理论图代替效果。

## 9. 声音、UI 和心理舒适度
建立 `AudioDirector`：风/雪、远车、脚步、室内水壶、暖气轻响、纸袋、钱币/木柜的音量层次；音乐稀疏、不循环轰炸；动态范围可调、音效可单独关闭、系统声音焦点合理。**适当的寂静是作品的一部分**。禁止频繁提示音、过量闪烁与强制动画。

主菜单为大片负空间与画面中央很小的路边便利站，不采用华丽角色合照或铺满的按钮；标题与开始/继续/设置/好友开店应简洁、可读。店内与地图的操作图标、文字字阶、边框、可访问名称、安全区形成统一组件系统。让玩家知道下一步能做什么，但提示尽量贴合场景，不弹满屏指令。选择面板显示 2–4 个有真实差异的自然语言选择，支持“沉默/离开”，并清楚呈现不可用条件。

## 10. 工程模块和数据契约
在现有仓库基础上，将实现按职责组织为：`core/simulation`、`narrative/graph`、`narrative/runtime`、`actors/schedules`、`map/scene-graph`、`render/layers`、`animation/timeline`、`ui/interaction`、`audio/director`、`save/migrations`、`network/authority`、`tools/content-validator`、`tests`。这些是**目标边界**，不要求一次性重构完所有旧代码。先审视原仓库 `src/kiosk-core.js`、`src/kiosk-dialogue.js`、`src/kiosk-motion.js`、`src/kiosk-silhouette.js`、`src/network.js`、`src/kiosk-app.js`，识别保留、删除和迁移界面。

统一事件结构：`{eventId,sceneId,actorId,action,payload,worldRevision,timestamp}`；状态修改只有核心 reducer/房主权威执行，UI/动画不能私改库存、剧情旗标或关系。选择导致的修改幂等且可重放；剧情触发器对同一 `eventId` 恰好一次；客户端掉线重连后不会重复收款、重复发奖励或丢失角色事件。

保存：版本化 schema + 迁移脚本 + 兼容旧 v3 存档 + 自动存档/手动槽位 + 损坏备份/导入导出 + 存档回放。故事、世界、库存、主人公、NPC 记忆、角色日程、选项历史、已观看过场的可恢复状态均必须序列化；纯动画帧位和光雪随机粒子不用当权威持久数据。联机保持 1–4 人可选，但**单人文学体验优先**；多人选择冲突要有明确主持/协商机制，不为了多人功能牺牲单人可玩性。

## 11. 生产线、测试和内容审校（完成度靠证据）
建立角色资料表、对白 CSV/Ink 源、事件表、地图表、资产清单、动画状态表、音频清单、测试案例矩阵和发布日志；从数据文件可检测不再引用的素材、失效对白、永不到达剧情和漏翻文本。剧本文字先做内部朗读和删冗审校，再入库；不得自动量产同质对白凑数量。

自动化最低要求：
- `npm run check` / `npm test` 与内容验证；剧情图穷举有限条件组合，检测所有结局可到达、无死节点、失效 option、重复奖励和状态机卡死；
- Chromium 在 320×568、360×800、390×844、844×390、1280×720 上截图比较，确认无拉伸、画面越界、透明边污染、字被截、遮挡错误或非预期点击放大；
- 模拟真实触控的一夜闭环：启动 → 主菜单 → 进店 → 遇客 → 选择 → 交易 → 存档 → 退出 → 重新进入 → 回访与后果；至少一次中途断网、前后台切换和页面刷新；
- 多人用两个**真实浏览器客户端**完成共享对白、物品交接、房主权威结算和掉线重连，不以 fake mock 结果代替；
- 性能：记录主流移动端帧率及加载时间；以 30 FPS 最低可玩、稳定争取 60 FPS 为目标；减少大图/过量粒子，异步加载与缓存有诊断面板；
- Android 构建要区别 WebView 测试 APK 与原生游戏，不虚报真机验收。GitHub Actions 中上传真实游戏截图、测试记录和可装测试包，只有全部必须测试通过才部署网页。

**质量评审维度**：情绪与文学（文本是否有真实人味）；审美（构图/轮廓/颜色/光影）；交互（毫无多余点击）；叙事因果（昨天选项影响明天）；真实感（角色日程不冲突）；动画连贯；地图一致；技术稳定。出现问题必须先修，再扩内容。质量评价应引用具体截图、玩家输入轨迹和剧情路径，不许只靠“感觉已经很高级”。

## 12. 严格里程碑及验收口径
**M0｜诊断与设计**：写完整世界圣经、美术圣经、流程图、技术决策记录、地图/剧情/角色数据 schema，针对旧版列“删除/重用/重写”。交付故事开场的 1 个可观赏且可互动的真实画面示范。

**M1｜一晚完整纵向切片**：男女主角可选、一张可交互店内场景、一处可见街景、2 位有不同性格且会回访的 NPC、至少一条三步延迟后果的选项链、完整交易与递物动画、保存/恢复、声音设计、实机截图与浏览器测试。不得把只有文字菜单的原型宣布为完整切片。

**M2｜小型完整版**：完成 3–5 个高质量营业日、4 个可访问区域、至少 4 名角色的阶段性变化、一个分支汇合与一段可到达的完整结局预览；演出、互动和美术达到统一基准。此时再评估真实开发速度调整整个游戏内容目标。

**M3｜完整内容与系统**：所有正式地图/核心故事/结局、人物日程/记忆/选择影响、动画/声音、本地化文本和联机操作实际接通；逐条核对缺失表。禁止通过添加“未实装”菜单冒充完成。

**M4｜商业级完成度验收**：完整从开始到结局通关数次，覆盖全部关键分支；收集截屏、录屏与测试数据，修复崩溃、存档毁损、断线、文字溢出、视觉错层、角色穿帮、剧情矛盾、疲劳交互、无意义流程；导出版本化发行说明及可重复构建。未满足门槛时标记 Beta/测试版，不得自称发行完成。
