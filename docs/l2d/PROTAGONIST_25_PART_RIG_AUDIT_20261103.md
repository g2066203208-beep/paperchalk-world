## 结论

1. ZIP 中 **17 正面 + 8 背面** 独立 RGBA PNG，全都保留图层顺序、画布坐标、可见性、透明度及 ID。
2. ZIP 的 25 条 manifest **没有** `parentId/pivot/mesh/bones/weights/deformers/parameters` 字段；即没有可恢复的真正单部件骨架或绑定工程。
3. `studio.js#persistSkeleton()` 仅保存 `name,x,y,opacity,visible,image`，不是逐关节绑骨模型。
4. `rig.js#psdTarget()` 用 **文字名称正则** + 时间正弦计算位移，没有从项目读取真实轴点、父骨骼、权重、关键形。
5. `rig.js#drawBoneRig()` 绘制约定常量 `joints` 和 `chains`，不是单层对象实际的 bone/deformer 关系。
6. 工作室女主默认使用 V4 逐帧动画。托管原始 17+8 PNG 能编辑像素，不意味着已经在当前游戏中逐层驱动；`hasNativePSD` 还要求 `role==='psd-part'` 且最少 12 层，而该原始 ZIP 的 role 为分类标签（如 `hair_back`、`arms`），因此默认不进入“真实 PSD 骨骼”模式。
7. 不能再把“可单独选择图层”“独立 PNG 素材”“动态 V4 逐帧”称为“已经做了可编辑 Live2D 绑骨”。

## 素材数据 ≠ 可编辑 Live2D Rig

**应该存在但当前没有的逐层字段与工具：**

- `partId`、`parentId`、独立的 `pivot`（旋转中心）、`restPose`；
- 单层的 ArtMesh 顶点、UV、三角形、局部和全局坐标；
- 骨骼层级、Bone 权重（每顶点归一）、IK/FK 或 Warp/Rotation Deformer；
- Breath、Hair、Skirt、Arm、Eye、Mouth 等参数的绑定目标和多关键形；
- 曲线/物理与碰撞、稳定的 `seek(time)`、真实编辑器选点/拖骨骼；
- 浏览器编辑器与游戏的同一个可序列化 Rig JSON，包括手工调整与撤销历史。

**必须区别：**
- 已完成：原始 PNG 分层资产及像素编辑；V4 128 帧兼容播放。
- 部分实现：按名称规则将单个 PNG 进行仿射或三角网格形变。
- **未完成：** 每个部件可独立检查、拖动和保存轴点、骨骼、权重、变形器、参数关键形的专业 Rig 工程。

## 纠偏顺序

1. **保持原始 25 层不变。** 不额外复制衣领、脖颈，不对原动画盲改。
2. 用每层固定 `id` 和角色视角取代名称正则；分别审查上述 25 个部件的静止合成像素、遮挡、alpha 空洞，尤其是前颈与背发/覆盖发片。
3. 创建逐部件可持久化的 Rig 数据结构。不能只有一个全局幅度和统一 mesh 正弦。
4. 先给可独立控制的真实分层轴点、网格顶点、参数 Keyform 和编辑/保存能力；各层修好才能加头发裙摆惯性。
5. 逐层比对“参数归零完全原样”“只动选中层其他层稳定”“极限角度不露缝/穿模”，并真正打开游戏验证。

本审计无权查看用户设备浏览器 **IndexedDB/localStorage** 内的私人手工配置，不能冒充“已检视用户本机每层历史修改”。未经其项目导出，只能确认 GitHub 托管基础分层和当前引擎源代码。
